# API guide

How to use the merchant onboarding service. The service has one endpoint, `POST /merchants`. Examples use `curl` against `http://localhost:3000`. Data is kept in memory, so restarting the server clears all merchants.

## Register a merchant

`POST /merchants` with `Content-Type: application/json`.

### Request fields

| Field | Type | Required | Rules |
|---|---|---|---|
| `companyName` | string | yes | Trimmed. 2 to 200 characters. |
| `contactEmail` | string | yes | Trimmed. Must be a valid email address, at most 254 characters. |
| `country` | string | yes | Trimmed. Exactly two letters. Stored in uppercase (`gb` becomes `GB`). Not checked against the list of real ISO country codes. |
| `externalMerchantId` | string | yes | Trimmed. 1 to 100 characters. Must be unique, ignoring letter case. |
| `confirmSimilar` | boolean | no | Set to `true` to register a merchant even though it looks similar to an existing one. Not saved and not returned. |

Other fields are ignored. For example, a `status` sent by the client is dropped. The whole request body can be at most 100 KB.

### Responses at a glance

Every error response has the same shape: `error` is a stable code for programs, `message` is text for people, and some errors add more fields (`details`, `similarMerchants`).

| Status | `error` | Meaning | What to do |
|---|---|---|---|
| `201` | none | Merchant created. | Nothing. |
| `400` | `VALIDATION_ERROR` | One or more fields are invalid. | Fix the fields listed in `details`. |
| `400` | `INVALID_JSON` | The body is not valid JSON. | Fix the JSON. |
| `409` | `DUPLICATE_MERCHANT` | `externalMerchantId` is already registered. | Use a different ID. `confirmSimilar` cannot override this. |
| `409` | `SIMILAR_MERCHANT_FOUND` | Looks like an existing merchant. Nothing was saved. | Check the listed merchants. If it is a different merchant, resend with `confirmSimilar: true`. |
| `400`, `415` | `BAD_REQUEST` | Another problem with the request itself, such as an unsupported `Content-Encoding`. | Fix the request. |
| `413` | `PAYLOAD_TOO_LARGE` | The body is larger than 100 KB. | Send a smaller body. |
| `404` | `NOT_FOUND` | The path or method does not exist. Only `POST /merchants` is available. | Check the URL and method. |
| `500` | `INTERNAL_ERROR` | Unexpected server error. | Retry later or check the server log. |

## Success: 201 Created

```bash
curl -i -X POST http://localhost:3000/merchants \
  -H 'Content-Type: application/json' \
  -d '{"companyName":"  Northstar Ltd ","contactEmail":"ops@northstar.example","country":"gb","externalMerchantId":"northstar-001"}'
```

```json
{
  "id": "c9f837c1-9ba9-45fb-92ca-4cf45c714476",
  "companyName": "Northstar Ltd",
  "contactEmail": "ops@northstar.example",
  "country": "GB",
  "externalMerchantId": "northstar-001",
  "status": "PENDING",
  "createdAt": "2026-11-19T14:47:43.985Z"
}
```

| Field | Meaning |
|---|---|
| `id` | Identifier generated by the service (UUID). Different from `externalMerchantId`. |
| `companyName`, `contactEmail`, `externalMerchantId` | The values you sent, after trimming. |
| `country` | Uppercase. |
| `status` | Always `PENDING` for a new merchant. |
| `createdAt` | Creation time, ISO 8601, UTC. |

## Validation error: 400

```bash
curl -i -X POST http://localhost:3000/merchants \
  -H 'Content-Type: application/json' \
  -d '{"companyName":"A","contactEmail":"nope","country":"GBR"}'
```

```json
{
  "error": "VALIDATION_ERROR",
  "message": "The request body is invalid. See details for each field",
  "details": [
    { "field": "companyName", "message": "must be at least 2 characters" },
    { "field": "contactEmail", "message": "must be a valid email address" },
    { "field": "country", "message": "must be a two-letter country code" },
    { "field": "externalMerchantId", "message": "is required" }
  ]
}
```

`details` lists every invalid field in one response, so you can fix them all at once. Each entry has the `field` name and a `message`. Messages are `is required` (missing), `must be a string` or `must be a boolean` (wrong type), or a rule such as `must be at most 200 characters`. A body that is not a JSON object (for example an empty body) gives `field: "(body)"` and the message `must be a JSON object`.

A body that is not valid JSON returns `{ "error": "INVALID_JSON", "message": "Request body is not valid JSON" }`.

## Duplicate ID: 409 DUPLICATE_MERCHANT

Sent when `externalMerchantId` matches an existing merchant. Matching ignores letter case and surrounding spaces, so `Northstar-001`, `northstar-001` and ` NORTHSTAR-001 ` are the same ID.

```json
{
  "error": "DUPLICATE_MERCHANT",
  "message": "A merchant with externalMerchantId \"northstar-001\" is already registered"
}
```

## Similar merchant: 409 SIMILAR_MERCHANT_FOUND

The ID is new, but the company name or contact email matches a merchant that is already registered. This may be a repeat registration of the same merchant, so the service asks for confirmation. **Nothing is saved when this is returned.**

Example. The merchant from the first example exists. Now register the same company under a new ID:

```bash
curl -i -X POST http://localhost:3000/merchants \
  -H 'Content-Type: application/json' \
  -d '{"companyName":"NORTHSTAR, Limited","contactEmail":"x@other.example","country":"GB","externalMerchantId":"northstar-002"}'
```

```json
{
  "error": "SIMILAR_MERCHANT_FOUND",
  "message": "This merchant looks similar to an existing registration. Resend with \"confirmSimilar\": true to register it anyway",
  "similarMerchants": [
    {
      "id": "c9f837c1-9ba9-45fb-92ca-4cf45c714476",
      "companyName": "Northstar Ltd",
      "externalMerchantId": "northstar-001",
      "reasons": ["SAME_COMPANY_NAME"]
    }
  ]
}
```

| Field | Meaning |
|---|---|
| `similarMerchants` | Existing merchants that look like the new one. |
| `similarMerchants[].id` | The service `id` of the existing merchant. |
| `similarMerchants[].companyName` | Its company name. |
| `similarMerchants[].externalMerchantId` | Its external ID. |
| `similarMerchants[].reasons` | Why it matched (see below). |

### Reasons

| Reason | Rule |
|---|---|
| `SAME_COMPANY_NAME` | Names are equal after lowercasing, removing accents and punctuation, collapsing spaces and dropping trailing legal suffixes (`Ltd`, `Limited`, `LLC`, `Inc`, `Corp`, `GmbH` and similar). `Northstar Ltd` and `NORTHSTAR, Limited` match. `North-Star` does not match them, because the hyphen becomes a space (`north star`). |
| `SAME_CONTACT_EMAIL` | Email addresses are equal ignoring letter case. |

A merchant can match for both reasons. Names that only look alike (`Northstar` and `Northstar Logistics`) do not match.

### Confirming

If you checked and this is a different merchant, send the same request again with `"confirmSimilar": true`:

```bash
curl -i -X POST http://localhost:3000/merchants \
  -H 'Content-Type: application/json' \
  -d '{"companyName":"NORTHSTAR, Limited","contactEmail":"x@other.example","country":"GB","externalMerchantId":"northstar-002","confirmSimilar":true}'
```

This returns `201` with the new merchant. `confirmSimilar` is only an instruction for this request. It does not appear in the response and is not stored.

`confirmSimilar` only skips the similarity warning. It does not skip validation or the duplicate ID check, so a request with an existing `externalMerchantId` still returns `409 DUPLICATE_MERCHANT`.

If the merchant is a true repeat, do not resend. Use the existing merchant listed in `similarMerchants`.

## Suggested client flow

1. Send the registration without `confirmSimilar`.
2. On `201`, done.
3. On `400`, fix the fields in `details` and retry.
4. On `409 DUPLICATE_MERCHANT`, use a different ID, or stop if the merchant is already registered.
5. On `409 SIMILAR_MERCHANT_FOUND`, show `similarMerchants` to the user. If the user confirms it is a different merchant, resend with `confirmSimilar: true`.

The service remembers nothing between steps 1 and 5. The second request is checked from scratch, so a merchant added in between can change the result.
